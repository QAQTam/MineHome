# 米家鸿蒙中间件设计（@miot/sdk + mijia-core）

> 前置：协议面已用 Python 原型实测闭环（见 协议面分析报告.md §10）。
> 本文档定义 ohos-rs + ArkTS 的中间件分层、API 契约与测试策略。

## 1. 分层

```
┌─ ArkTS UI（设备卡片/控制页/场景）
├─ ArkTS @miot/sdk —— Promise 领域 API + 事件订阅（Device/Property 模型）
├─ NAPI 桥（napi-rs）
└─ ohos-rs mijia-core（纯 Rust crate，可独立 cargo test）
    ├─ auth     登录/通知确认/passToken 续期/session 持久化
    ├─ cloud    RC4 签名请求器 + 响应解密
    ├─ device   设备列表缓存 / spec 属性读写
    └─ transport（二期）miio UDP / lan_dm / 中枢 TLS
```

规则：
- 协议细节（RC4/nonce/签名串/响应头）只存在于 cloud 层，不向上泄漏
- ArkTS 只见领域模型（Device/Property/Scene），不见 "rc4_hash__" 这类协议字段
- mijia-core 不依赖任何鸿蒙 API（纯 Rust + tokio + reqwest），可在 PC 上 cargo test

## 2. API 契约（v0.1）

### Rust: mijia-core
```rust
pub struct Session { pub user_id: String, pub ssecurity: String, pub service_token: String,
                     pub server: Server }            // cn/sg/us/de
pub enum LoginFlow { Direct, NeedNotification { url: String } }

impl MiHome {
    pub fn new(session_path: impl AsRef<Path>) -> Self;
    pub async fn login_password(&self, user: &str, pass: &str) -> Result<LoginFlow>;
    pub async fn finish_notification(&self, pass_token: &str, user_id: &str) -> Result<Session>;
    pub async fn list_devices(&self) -> Result<Vec<Device>>;             // 缓存 + 刷新
    pub async fn get_properties(&self, did: &str, props: &[(i32, i32)]) -> Result<Vec<PropValue>>;
    pub async fn set_properties(&self, did: &str, props: &[(i32, i32, Value)]) -> Result<()>;
    pub async fn call_miio(&self, did: &str, method: &str, params: Value) -> Result<Value>;  // 老协议
}
pub struct Device { pub did: String, pub model: String, pub name: String,
                    pub online: bool, pub spec: Option<serde_json::Value> }
```

## 3. 测试策略（三层）

1. **core 对拍夹具**（最关键）：Python 原型（mijia_proto.py）生成固定输入输出 → JSON 夹具 →
   cargo test 对比 signature/enc_data/decrypted 字节级一致。覆盖：
   - gen_nonce / session_security / client_sign / sign() 串 / RC4 请求加密 / 响应解密
2. **中间件 mock**：transport trait 注入假 HTTP，测 list_devices/set_properties 的编排逻辑
3. **集成冒烟**：`--live`（需真实 session.json），仅 devices + switch off

对拍基准脚本：`tools/gen_fixtures.py`（调用 mijia_proto 的函数生成 vectors.json）

## 4. 实现顺序

1. mijia-core: rc4/签名/nonce/会话（纯函数）+ 对拍测试 ← 先做，不碰网络
2. mijia-core: cloud 请求器（reqwest）+ auth 流程（含 NeedNotification 分支）
3. mijia-core: device 服务
4. napi-rs 绑定 + ArkTS @miot/sdk 类型与包装
5. 鸿蒙工程接线 + 真机冒烟
6. （二期）miio UDP 直连 / 网关子设备 / 中枢 TLS

## 5. 已钉死的协议细节（移植必读）

见 协议面分析报告.md §10，要点：
- clientSign = b64(SHA1("nonce=<十进制>&" + ssecurity))；请求 `location&clientSign=...&_userIdNeedEncrypt=true`
- serviceToken 在响应头 `xiaomiio_serviceToken`；body 为 'ok'
- securityStatus=16 → 通知确认分支（App 用 WebView；headless 可用系统浏览器）
- 请求：RC4 key=b64d(sessionSecurity) drop1024，连续加密 data→rc4_hash__；form 五字段
- 签名串："POST&<path 不含 /app>&data=...&rc4_hash__=...&sessionSecurity" → b64(SHA1)
- 响应：b64 → 全新 RC4(b64d(sessionSecurity)) drop1024 → JSON
- cookie: userId + serviceToken（其余 locale/timezone 可选）
- 老协议 /home/rpc/<did>：form 单 data 字段 + 可选头 MIOT-REQUEST-MODEL
