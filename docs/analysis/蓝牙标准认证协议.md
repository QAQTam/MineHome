# 米家标准蓝牙认证协议（酷态科充电器实测闭环）

> 2026-11-17 实测设备：酷态科10号超级电能充Ultra（`njcuk.fitting.ad1204`）
> did=`<did-充电器>`，MAC=`AA:BB:CC:DD:EE:02`，pid=6（BLE 直连），固件 `2.1.2_0073`
> 实测脚本：`_work/ble_login.py`（bleak，PC 侧）；逆向来源：米家 APK v11.9.705 反编译源

## 0. 结论速览

```
登录 = GATT + 分片通道 + HKDF/HMAC 三层，全部复刻成功：
1. GATT 服务 0xFE95
2. 0x0010 = 裸命令通道（opcode 无流头）；0x0019 = 分片流通道（含 ACK 状态机）
3. key = 云端 device token（12B 原始值！不是 beaconkey/bindkey）
4. okm = HKDF-SHA256(ikm=token, salt=appRandom||devRandom, info="mible-login-info", 64B)
5. dev_confirm  = HMAC-SHA256(okm[0:16],  dev||app)   —— 设备发，app 校验
   app_confirm  = HMAC-SHA256(okm[16:32], app||dev)   —— app 发，设备校验
   （注意：APK 反编译里 app_confirm 看似用 okm[0:16]，实测设备认 okm[16:32]）
6. session_key = 完整 64B okm
```
7. **0x001B 数据推送已完全解密（2026-11-22）**：AES-CCM（key=okm[0:16]，
   nonce=okm[32:36]+0000+sn+roll，M=4/L=3/无AAD），明文 = miot SPEC v2 帧；
   端口信息 u32 = [state][协商上限][I×0.1A][V×0.1V]，实测与屏幕对拍
   9.1V/1.1A（C1）、9V/1.9A（A 口）逐字节吻合，MIC 60/60 通过。详见 §8。
   Rust 落地：`mijia-core/src/ble_auth.rs`（cargo test 5/5）。
```

## 1. GATT 服务表（实测 dump）

服务 `0000fe95-0000-1000-8000-00805f9b34fb`：

| char | 属性 | 角色 |
|---|---|---|
| 0x0004 | read | 设备信息（固件版本 ASCII `2.1.2_0073`） |
| 0x0005 | read+notify | 空读（profile 必查位） |
| **0x0010** | write-noRsp+notify | **命令通道**：裸 opcode（0x24 login start、0x13/0x14 bind result）；结果码 0x21 成功 / 0x22、0x23、0xE0、0xE2 拒绝 |
| **0x0019** | write-noRsp+notify | **认证流通道**：type 10=appConfirm、11=appRandom、12=devConfirm、13=devRandom（双向，带分片状态机） |
| 0x0017/0x0018/0x001A-0x001C | write+notify | MTU/OTA/私有通道（本期未用） |

## 2. 分片流通道 wire 格式（eh2 层，实测钉死）

```
CMD start（发起流）:  0000 00 <type> <frameCount u16 LE>
ACK（收到后回）:      0000 01 <status> [<seq u16 LE> ...]
数据帧:              <seq u16 LE> <payload ≤18B>     seq 从 1 起
单帧直达:            0000 04 <type> <payload>        （mng；本次设备未用）

ACK status 语义（o0ooOOo 类）:
  1 = "准备收"（收到 CMD start 后立即回，与帧数无关！）
  0 = "收齐"（收满 frameCount 帧后回一次；逐帧不回 ACK）
  5 = "丢帧" + 丢失 seq 列表（请求重传，实测出现过一次误报，后续帧补齐后自行恢复）

帧大小：设备侧固定 18B/帧（devConfirm 32B → fc=2）
```

**血泪教训**：ACK status=1 是"准备收"不是"剩余帧数"；逐帧 ACK 是错的，只在收齐后回一次 status=0。逐帧乱 ACK 会让设备静默卡死。

## 3. 登录流程（实测成功序列）

```
App                                      Device
 │ write 0x0010: 24 00 00 00 (login start) │
 │ ──────────────────────────────────────→ │
 │ 0x0019 flow: 0000 00 0B 0100 (type11)   │
 │ 0000 01 01 ←─────────────────────────── │ (ACK 准备收)
 │ 0100 <appRandom 16B> ─────────────────→ │
 │ 0000 01 00 ←─────────────────────────── │ (ACK 收齐)
 │                                          │
 │ ←──────── 0000 00 0D 0100 (devRandom)   │
 │ 0000 01 01 ──────────────────────────→  │
 │ ←──────── 0100 <devRandom 16B>          │
 │ 0000 01 00 ──────────────────────────→  │
 │                                          │
 │ ←──────── 0000 00 0C 0200 (devConfirm)  │
 │ 0000 01 01 ──────────────────────────→  │
 │ ←──────── 0100 <HMAC 前18B>             │

```

## 4. 密码学推导（实测验证）

```python
okm = HKDF_SHA256(ikm=token12B, salt=appRandom+devRandom, info=b"mible-login-info", L=64)
# RFC5869 标准 extract+expand；ikm/salt 均为原始字节流，无 hex/ascii 变换
dev_confirm  = HMAC_SHA256(okm[0:16],  devRandom + appRandom)   # 校验 PASS（逐字节一致）
app_confirm  = HMAC_SHA256(okm[16:32], appRandom + devRandom)   # 设备认这个（0x21）
session_key  = okm  # 64B 全量（后续 spec 通道加密用，待下一阶段实测）
```

- token 来源：`/v2/home/device_list_page` 的 `token` 字段（24 hex = 12B），**就是它**，无需 beaconkey/bindkey
- beaconkey（`/v2/device/blt_get_beaconkey`，16B）只用于 MiBeacon 广播解密，与登录无关
- `get_bindkey` 两次请求返回不同值 → 它是请求派生的临时密钥，与登录无关
- 设备每次连接**只评估第一个 appConfirm**，错了回 0x23 后静默 → 每连接只能试一个候选

## 8. 登录后的数据通道（0x001B）—— **已完全破解（2026-11-22）**

登录成功后约 12~20s，设备在 char 0x001B 主动推送状态包（插着负载时秒级周期推送）。
推送 = 流通道同款封装（0x001B 上）：CMD start `0000 00 00 0200`（pkg=0, 2帧）→ app 回 ACK(01)；
帧1 `0100 <18B>`；帧2 `0200 <3B>` → app 回 ACK(00)。

采集 79 个样本（同会话 okm，`_work/ble_1b_session.json`），**MIC 40/40 全部验证通过**。

### 8.1 密码学（反编译钉死，全部实测验证）

> 反编译源头：`_work/apk_src/sources/_m_j/e71.java`（spec 通道加解密）+
> `_m_j/i3g.java` OooOo0()（BouncyCastle CCMBlockCipher，"nonce must have length from 7 to 13 octets"）。

```python
# RX（设备→app，0x001B notify）
key_rx   = okm[0:16]
nonce_rx = okm[32:36] + b"\x00"*4 + sn_LE(2B) + roll_LE(2B)     # 12B
frame    = [sn u16 LE][ct (N-4)B][MIC 4B]
pt       = AES_CCM_decrypt(key_rx, nonce_rx, aad=None, M=4, L=3) # RFC3610

# TX（app→设备，0x001B writeNoRsp）
key_tx   = okm[16:32]
nonce_tx = okm[36:40] + b"\x00"*4 + sn_LE(2B) + roll_LE(2B)
out      = [sn u16 LE] + AES_CCM_encrypt(key_tx, nonce_tx, pt, M=4)
```

- `sn` u16 LE：**bit15 是 roll 翻转位**——相邻两包 bit15 翻转一次则 roll+1
  （`_m_j/d71.java`；本会话 sn=1..40 不触及 bit15，roll 恒 0）
- TX/RX 各自独立 sn（`d71` 四字段：rx_sn/rx_roll/tx_sn/tx_roll），连接建立时清零
- 之前"恒 0x00 的 [18] 字节 + 3B 尾"是**采集脚本 bug**：帧2 = `[seq u16][3B]`，
  `ble_collect.py` 对 len<18 的帧取了 `b[1:]`，把 seq 高字节（0x00）插进了流里。
  真帧 = 21B = `[sn 2B][ct 15B][MIC 4B]`（老 22B 结构表作废）

### 8.2 明文 = miot 标准 SPEC v2 帧（`com/miot/spec` + `_m_j/egh.Oooo0`/`cic`/`eyb`）

```
[0:2] u16 LE = (version << 12) | frame_len     # 实测 0x200f：ver=2, len=15
[2:4] u16 LE = tid                              # 设备侧流水号，本会话 149..188
[4]   u8      = opcode                          # 0=set 1=set_rsp 2=get 3=get_rsp
                                                # 4=properties_changed 5=action 6=action_rsp
                                                # 7=event_occured 0xF0=版本交换
[5]   u8      = object count                    # （opcode=4/7 时）
每个 object: [siid u8][piid u16 LE (ver≥2)][u16 LE = (vtype<<12)|vlen][value vlen LE]
SpecValueType: 0=bool 1=uint8 2=int8 3=uint16 4=int16 5=uint32 6=int32
               7=uint64 8=int64 9=float 10=string（全小端）
```

### 8.3 实测解码（三轮差分对拍，2026-11-22 定案）

40+6+14 个独立包全部是：`opcode=4 properties_changed`，1 个 object：
`siid=2 (charger) piid=1/2/3/4 (port-x-info) uint32`，spec 来源
`miot-spec.org urn:...:njcuk-ad1204:2`（`_work/spec_ad1204_v2.json`，gatt-access read+notify）。

**uint32 小端字节 `[b0 b1 b2 b3]` = `[端口state][协商上限字段][实测电流×0.1A][实测电压×0.1V]`**

差分证据（三轮采集，全部 MIC 验证通过）：

| 轮 | 口 | b3 (V×0.1V) | b2 (I×0.1A) | b1 | 屏幕 |
|---|---|---|---|---|---|
| S1 (80s) | C1 | 90/91 | 6..11 脉动 | 11 恒定 | 9.1V / 1.1A / 约10W |
| S2 | C1 | 90/91 | 11 | 10 | — |
| S3 (30s) | C1 | 90/91 | **8..9（电流缓降）** | **10 纹丝不动** | **9V / 0.9A** ✓ |
| S2' | A | 90 | **16→19（爬升）** | 112 | **9V / 1.9A** ✓ |

- `b2 = I×0.1A`：A 口 19 → 屏幕 1.9A 精确命中；S3 缓降 8/9 → 屏幕 0.9A ✓（铁证）
- `b3 = V×0.1V`：90/91 ↔ 屏幕 9.0/9.1V ✓
- `b1`：实测中不随负载电流变化（S3 电流 1.1→0.9A 时保持 10）→ 是**协商/合同值**
  （PD 口上 = 电流上限 0.1A 或合同功率 W，两种解释均自洽；A 口样例 112 疑似
  协议相关字段——非 PD 协议（QC/SCP 族）可能填电压 0.1V（11.2V）或协议档位，
  单位待固件级确认。**读 V/I 不需要它**）
- `b0 = 1`：端口 state（1=输出中）
- C1 空载时**完全不推送**（拔掉充电宝的 35s 窗口零包）→ 空载端口无 piid 推送
- tid：每次连接从一个小基数递增（会话1: 149..188，会话2: 1..，会话3: 13..）
- PPS 电压纹波：V 在 9.0/9.1V 之间跳 = 实测 9.05~9.14V 的 0.1V 取整

## 9. 探测记录（负样本，防重复劳动）
